# API Contract (v1, production REBOUND simulation)
Source of truth for schemas: `backend/models.py` (Pydantic); behaviour: `backend/simulation.py`, `backend/collisions.py`. Update this file in the same change as any API change.

**Status legend:** ✅ implemented (tested) · 🕓 planned (does NOT exist yet).

## Conventions
- **Units (SI, always, in every field):** mass `kg`; radius and position `m`; velocity `m/s`; simulation time `s`; G = `6.67430e-11 m^3 kg^-1 s^-2`. Unit is in the field name suffix (`massKg`, `radiusM`, `positionM`, `velocityMPerS`, `simulationTimeS`).
- **Coordinates:** one fixed, right-handed Cartesian frame (x × y = z). Positions and velocities share this frame. The origin is the simulation origin (not tied to any body). The frontend may scale/offset *rendered* distances for visualization but must never alter or send scaled values as API physics values.
- **Numbers:** JSON numbers, finite only. NaN/Infinity (and overflow such as `1e999`) are rejected.
- **IDs:** generated by the backend (`body-<12 hex>`), unique, never reused, stable across reads. Clients must not send `id`.
- **Colors:** `#RRGGBB` (6 hex digits, case-insensitive; stored as sent).
- **Unknown request fields are rejected** (422).
- **Request bounds (422 outside):** `massKg` ∈ (0, 1e45]; `radiusM` ∈ (0, 1e15]; each `positionM` component |.| ≤ 1e18; each `velocityMPerS` component |.| ≤ 299792458 and total speed < c; `dtS` ∈ [1e-6, 1e8]; `name` 1–64 chars. Responses are not bounded: evolved state is reported as the engine has it.
- **Error shapes:** 422 `{"detail": [{"loc": ["body","massKg"], "msg": "...", "type": "greater_than"}]}` (validation); 404 / 409 / 500 `{"detail": "<message>"}`.
- **Base path:** backend serves `/api/v1/...` itself. Note: the Vite dev proxy currently *strips* `/api` (see Assumptions).

### Body
```json
{"id":"body-3f9a1c2b7d4e","name":"Earth","massKg":5.972e24,"radiusM":6.371e6,
 "positionM":{"x":1.496e11,"y":0.0,"z":0.0},"velocityMPerS":{"x":0.0,"y":29780.0,"z":0.0},"colorHex":"#3b82f6"}
```
`name`: 1–64 chars (display only; ids identify bodies).

### SimulationState
`{"status": "paused" | "running", "simulationTimeS": number, "bodies": [Body]}` — bodies in creation order (a merge survivor keeps its place in the order). **`status` is always `"paused"`**: the server never advances time on its own. Play is the client calling `POST /simulation/step` repeatedly; Pause is it stopping. `"running"` is reserved and never returned.

### Event
```json
{"id":"evt-1","type":"merger","simulationTimeS":99.26,"estimatedContactTimeS":99.1185,
 "bodyIds":["body-a","body-b"],"resultBodyId":"body-a","resultMassKg":3000.0,
 "relativeSpeedMPerS":2.0,"kineticEnergyLostJ":1333.33,"spinAddedKgM2PerS":{"x":0,"y":0,"z":-666.67}}
```
- `type`: only `"merger"` exists. Every detected overlap is resolved as a perfectly inelastic merger (no bounce, no fragmentation), so a separate `collision` event would carry no extra information and is not emitted.
- `simulationTimeS`: engine time at which the overlap was **detected** (end of an internal integrator step). It is NOT the contact time. `estimatedContactTimeS` is a straight-line back-extrapolation (exact for gravity-free motion, otherwise accurate to the path curvature within one step; `null` if no estimate exists). Do not present either as an exact timestamp.
- `bodyIds` = `[survivor, absorbed]`; `resultBodyId` = survivor (the heavier body; ties: the engine's first particle). The absorbed id is deleted and never reused. The survivor keeps its id, name and colour and gets the combined mass, centre-of-mass position and velocity, and a volume-conserving radius.
- `kineticEnergyLostJ` = ½μv_rel² of translational energy; it is not conserved (there is no heat/internal-energy model, it is only summed in a server-side ledger). `spinAddedKgM2PerS` = orbital angular momentum μ(r_rel×v_rel) booked as remnant spin: bookkeeping only (no rotation, no spin energy, no tides).
- Event ids `evt-<n>` increase for the process lifetime (not reused after reset). The server keeps the latest 1000 events.

## Endpoints

### ✅ `GET /healthz`
Liveness probe. (Legacy `GET /health` has the same response.) Response 200: `{"status":"ok"}`.

### ✅ `GET /api/v1/simulation/state`
Authoritative snapshot (D-001). Response 200: SimulationState. Fresh server: `{"status":"paused","simulationTimeS":0.0,"bodies":[]}`.

### ✅ `POST /api/v1/bodies`
Add a body at the current simulation time. Request: Body without `id`. Response **201**: the Body with its generated `id`.
Errors: 422 (validation/bounds; unknown field including `id`); **409** if the new sphere would overlap an existing body (centre distance < r₁+r₂, because a zero-separation start corrupts the engine) or 200 bodies already exist.

### ✅ `PATCH /api/v1/bodies/{body_id}`
Partial update; any subset of `name, massKg, radiusM, positionM, velocityMPerS, colorHex` (vectors are replaced whole), at least one, none `null`; `id` is immutable. Physical changes take effect from the current simulation time. Response 200: the full Body.
Errors: 404 unknown (or merged-away) id; 422 validation (empty body, null, unknown field, bounds); 409 if the new position/radius would overlap another body. A rejected request changes nothing.

### ✅ `DELETE /api/v1/bodies/{body_id}`
Remove a body. Response 204, no body. Errors: 404 unknown id.

### ✅ `POST /api/v1/simulation/step`
Advance simulation time by `dtS` seconds using REBOUND IAS15 (bounds above; a larger request is a 422, so the client loops). Request `{"dtS": 3600.0}`.
Response 200: SimulationState plus
```json
{"status":"paused","simulationTimeS":3600.0,"bodies":[...],"advancedS":3600.0,"events":[Event, ...]}
```
`events` holds only events that occurred during this call (merged-away bodies are already missing from `bodies`; use `events[].bodyIds`). `advancedS` equals `dtS` up to rounding.
The step is transactional: if the engine raises, a collision callback fails or any state becomes non-finite, the state from before the call is restored and the response is **500** `{"detail":"simulation step failed and was rolled back: ..."}`. Requests are serialized by a lock (concurrent steps queue, never interleave). A step is not interruptible (see limitations).
Errors: 422 bad `dtS`; 500 as above. There is no 409 "running" case: the server never runs by itself.

### ✅ `POST /api/v1/simulation/reset`
Remove all bodies and events, time back to 0. Deterministic: the same inputs afterwards give the same results as a fresh server. Response 200: `{"status":"paused","simulationTimeS":0.0,"bodies":[]}`. Body ids are never reused; event ids continue counting.

### ✅ `GET /api/v1/events`
Response 200 `{"events":[Event, ...]}`, oldest first (latest 1000 since the last reset).

### Withdrawn / planned
- `POST /simulation/start` and `/simulation/pause`: **not implemented and no longer planned**; Play/Pause is client-side scheduling of `step` requests.
- 🕓 Checkpoint save/restore: not specified (REBOUND restore works, but the resolver, ledgers and event log would have to be rebuilt; M0.6).

## Engine behaviour the client can rely on
- Newtonian point-mass gravity among all bodies, G = 6.67430e-11, IAS15 (adaptive). Radius matters only for collisions. No other forces, no relativity, no tides.
- Each `step` is integrated in chunks short enough that a_rel·dt²/8 ≤ 1% of each pair's contact distance (so `line` collision detection stays valid), at most 2000 chunks per request (beyond that chunks are longer than the criterion asks).
- Simultaneous collisions resolve in a fixed (seeded) order. A merge conserves mass and linear momentum to round-off (tested ≤ 1e-12 relative).
- Editing a body mid-simulation (mass/position/velocity/radius) restarts the integrator's internal state; conservation is not claimed across the edit itself.

## Physics limitations
- A merge does not conserve kinetic+potential energy or modelled angular momentum; both are bookkept (event fields, server ledgers) but no spin dynamics exist.
- Event times are detection times at integrator-step granularity; contact time is an estimate.
- `line` detection assumes near-straight motion inside a chunk. Untested: very tight binaries or close three-body encounters with large dt, more than 3 simultaneous collisions, mass ratios beyond 1e11:1, latency at large N (IAS15 is O(N²); M0 measured ~5e2–1e3 steps/s at N=100).
- Doubles resolve ~3e-5 m at 1 AU, limiting collision-geometry accuracy for small bodies far from the origin.
- Two centres coinciding exactly mid-step (measure zero) end in a merge or a rolled-back 500, never in silent corruption (tested for one geometry).
- A step has no wall-clock limit. Very small radii with very close non-colliding encounters can make IAS15 take very many tiny steps.
- State is in-memory, single process, lost on restart; no authentication; at most 200 bodies.

## Assumptions / known issues
- **Vite proxy mismatch:** `frontend/vite.config.ts` strips `/api` while the backend serves `/api/v1/...`; owned by the frontend session (T-008).
- Bounds on mass/radius/position are generous sanity limits, not physical claims.
